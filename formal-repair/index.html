把 25 局的 Lean 证明修到内核可查、规则真能算

每局封存时都有一份 Game.lean：把 agent 学到的规则写成 Lean，再证明「规则与录像一致」「照规则能通关」。 2026-09-28 复查发现，这批文件大多靠 native_decide（把编译器塞进可信基）、靠查表走路线、或只证了游戏的尾巴。 这一页记录把它们逐局修好的结果：25/25 局已登记修好，其中 23 局在本机检查器上全绿。

修好是什么意思

判据写于开修之前、写完即冻结，由脚本机械判定，不采信任何自述：

  • 编得过、可信基干净：Lean 4.30.0-rc2 下编译通过；证明一律 decide +kernel，两条定理的公理只许 propext / Classical.choice / Quot.sound，实际全部只用到 propext。
  • 数据没动过：数据段要么与原文件相同，要么由生成器从同一批原始录像重新生成、检查器逐行复算对得上。
  • 规则不是空话：每条规则的名字取自该局概念册，在录像上至少命中一次，不许恒真。
  • 靠规则算，不靠查表：关卡内的每一步都由 stepRules 从当前状态算出来；只有换关（新关布局是游戏内容）和重开允许查表，查了多少步照实写出。
  • 整局通关：路线从第 0 关起、一直走到 WIN，不是只证最后一段。

机械判据之外，每局还由一个没参与修复的审计 agent 对抗性复查（找反例、做改错实验、核公示），主会话再复跑检查器；两者都过才登记。 审计查出的问题不删不改，修完后写进 Game.lean 头注的「公示」。

途中改过的判据

  • R1 允许隐藏状态（用户裁决）：lp85、ft09 实测「单帧像素决定不了下一步」（计数条只取决于本关点了几次），允许在状态里加隐藏累加器和每关常数；同时禁止以「不预测」为名排除任何字段。
  • R2 客户端超时重发（用户裁决）：g50t 的一处怪异查明是客户端 60 秒超时后重发了请求；按外生输入建模，语义按每局数据定（g50t 是计数多一拍，sp80 是动作被执行两次）。
  • R3 路线可含关内重开（用户裁决，仅兜底）：只用于 s5i5；审计随后按关拼出了不含重开的 406 步路线，说明它只是生成器口径下的兜底。
  • R4 生成器修复：同一动作既有带坐标也有不带坐标两种写法时拆成两个构造子（只影响 sp80）。
  • 潜在状态例外（用户裁决）：隐藏量若需要推演，必须 Lean 独立写出同一规律、附改错实验、公示只靠隐藏字段自证的步数。
